# سانس‌یار | حساب و برنامهٔ سانس‌های ورزشی

اپ وب فارسی برای مدیریت حساب باشگاه و رزرو سانس زمین. رابط از Firebase Authentication، Cloud Firestore و Firebase Storage پشتیبانی می‌کند. اگر اتصال Firebase پیکربندی نشده باشد، برنامه در **حالت نمایشی محلی** اجرا می‌شود و داده‌ها به Firebase فرستاده نمی‌شوند.

## اجرای محلی

```bash
npm install
npm run dev
```

برای ساخت نسخهٔ انتشار:

```bash
npm run build
```

## راه‌اندازی Firebase

1. در [Firebase Console](https://console.firebase.google.com/) پروژه و Web App بساز؛ در Authentication روش‌های **Email/Password** و **Google** را فعال کن و دامنهٔ سایت را در Authorized domains اضافه کن. هر حساب با UID خودش عضو یک یا چند باشگاه می‌شود؛ ایمیل‌های ثابت برای تعیین نقش یا دسترسی وجود ندارد. اگر حساب Email/Password موجود داری و ایمیل Google همان ایمیل را دارد، ابتدا با رمز قبلی وارد شو و از حساب داخل برنامه Google را پیوند بده تا UID و عضویت‌ها حفظ شوند.
2. Firestore Database و Storage bucket بساز و Rulesهای `firestore.rules` و `storage.rules` را بازبینی کن. داده‌های خصوصی بر پایهٔ عضویت UID و UID حساب بازیکن محدود می‌شوند؛ کد دعوت فقط نام باشگاه را پیش از عضویت نشان می‌دهد.
3. تنظیم‌های Firebase Web App را وارد محیط انتشار یا از «تنظیم اتصال Firebase» داخل برنامه وارد کن. متغیرهای نمونه در `.env.example` هستند؛ برای انتشار محلی می‌توانی آن را به `.env.local` کپی و مقدارها را تکمیل کنی. برای Web Push، `VITE_FIREBASE_MESSAGING_SENDER_ID` الزامی است. فایل `.env.local` را در Git قرار نده.
4. اگر ورود در دامنهٔ انتشار انجام نمی‌شود، دامنهٔ دقیق را در Authentication → Settings → Authorized domains اضافه کن. برای اعلان مرورگر، سایت باید HTTPS باشد (به‌جز `localhost`) و کاربر باید اجازهٔ اعلان بدهد.
5. برای تنظیم Web Push، در Project settings → Cloud Messaging یک Web Push certificate/VAPID key بساز و کلید عمومی را به `VITE_FIREBASE_VAPID_KEY` بده یا در پنجرهٔ «تنظیم اتصال Firebase» برنامه وارد کن. این کلید عمومی است؛ service account یا کلید خصوصی را در برنامه قرار نده.
6. قواعد را با Firebase CLI منتشر کن. برای نمونه، پس از انتخاب پروژهٔ خودت با `firebase use <PROJECT_ID>`:

   ```bash
   firebase deploy --only firestore:rules,storage
   ```

   پیش از انتشار، Rules و تنظیم‌های امنیتی پروژه را بازبینی کن. تعداد باشگاه‌ها و اعضا در برنامه ثابت نشده است؛ نقش و محدودهٔ داده در هر باشگاه از عضویت UIDمحور همان باشگاه می‌آید. اگر پروژهٔ Firebase از نسخهٔ قبلی داده دارد، پیش از اعمال این Rules باید برای UIDهای معتبر اسناد `clubs/{clubId}/members/{uid}` و `users/{uid}/clubMemberships/{clubId}` و کدهای `clubInvites/{clubId}` یک‌بار provision شوند؛ این کار به‌صورت خودکار با ایمیل حدس زده نمی‌شود. سوابق قدیمی دارای `createdByUid` برای سازگاری خوانده می‌شوند.

### انقضا و اعلان Push در محیط واقعی

`functions/index.js` شامل سه Cloud Function است: انقضای دوره‌ای درخواست‌ها، callable امن برای مصرف ماندهٔ حساب با `clubId` و `bookingId`، و فرستادن اعلان‌های Firestore به توکن‌های FCM همان دریافت‌کننده. برای آن‌ها به Cloud Functions با runtime **Node.js 20** و طرح صورتحساب/سرویس‌های لازم Firebase (از جمله Cloud Scheduler برای تابع زمان‌بندی‌شده) نیاز است. ممکن است هزینه داشته باشد؛ تنظیمات صورتحساب و منطقه را در کنسول پروژه بررسی کن. زمان اجرای زمان‌بندی‌شده روی `Asia/Tehran` است و توابع در `europe-west1` مستقر می‌شوند.

پس از ساخت نسخهٔ وب و تنظیم `VITE_FIREBASE_VAPID_KEY`، توابع را منتشر کن:

```bash
firebase deploy --only functions
```

برای انتشار کامل وب و قواعد:

```bash
npm run build
firebase deploy --only hosting,firestore:rules,storage,functions
```

در `firebase.json`، Hosting از `dist` استفاده می‌کند. اعلان Push پس‌زمینه تا زمان تنظیم VAPID، اجازهٔ اعلان کاربر، ثبت توکن دستگاه و deploy موفق توابع آمادهٔ استفاده نیست. اعلان‌های درون‌برنامه‌ای به Firestore متکی‌اند. زمان‌بندی‌شدهٔ سرور مرجع آزادسازی مهلت‌هاست؛ انقضای کلاینتی هم برای بازخورد سریع‌تر وجود دارد، اما جای Cloud Function را نمی‌گیرد.

## باشگاه‌ها و عضویت

- هر حساب می‌تواند مالک یا بازیکن در هر تعداد باشگاه باشد؛ عضویت‌ها، تنظیم‌ها، پرداخت‌ها، سانس‌ها و رزروها در مسیر همان `clubId` جدا هستند. انتخاب باشگاه فعال فقط داده‌های همان باشگاه را بارگذاری می‌کند.
- مالک کد دعوت باشگاه را با بازیکنان به اشتراک می‌گذارد. بازیکن با ورود به حساب خودش و واردکردن کد عضو می‌شود؛ نقش و دسترسی از سند عضویت UIDمحور می‌آید، نه از ایمیل یا نام نمایشی.
- رزرو خصوصی، رسید، پرداخت، سانس، گفت‌وگو و اعلان فقط برای مالک همان باشگاه و حساب بازیکن مرتبط مجاز است. بازیکن فقط projection عمومی زمان/زمین/وضعیت سانس‌های عمومی را می‌بیند. رزرو مستقیم مالک در صورت انتخاب بازیکن به UID او وصل می‌شود.

## انتشار روی GitHub Pages

فایل `.github/workflows/deploy-pages.yml` نسخهٔ وب را از شاخهٔ `arena/f832e3ee-topch` می‌سازد و روی Pages منتشر می‌کند. پس از push، در GitHub برو به **Settings → Pages** و گزینهٔ **GitHub Actions** را به‌عنوان Source انتخاب کن. آدرس پروژه با تنظیم فعلی معمولاً `https://aminchat.github.io/topch/` خواهد بود.

در **Settings → Secrets and variables → Actions → Variables** متغیرهای `VITE_FIREBASE_API_KEY`, `VITE_FIREBASE_AUTH_DOMAIN`, `VITE_FIREBASE_PROJECT_ID`, `VITE_FIREBASE_APP_ID`, `VITE_FIREBASE_MESSAGING_SENDER_ID` و `VITE_FIREBASE_STORAGE_BUCKET` را وارد کن؛ `VITE_FIREBASE_VAPID_KEY` برای Web Push اختیاری است. در Firebase Authentication دامنهٔ `aminchat.github.io` را به Authorized domains اضافه کن. بدون تنظیم Web App، Pages در حالت نمایشی محلی بالا می‌آید و دادهٔ Firebase ذخیره نمی‌کند. Rules و Functions را جداگانه با Firebase CLI منتشر کن.

## رفتار رزرو

- مبلغ هر رزرو فقط از نرخ تنظیم‌شده در تنظیمات باشگاه می‌آید؛ بازیکن مبلغ تعیین یا تغییر نمی‌دهد و مالک نیز هنگام تأیید اولیه مبلغ جداگانه‌ای وارد نمی‌کند.
- درخواست بازیکن ابتدا حداکثر **۳۰ دقیقه** برای بررسی مالک سانس را قفل می‌کند. پس از تأیید اولیه، بازیکن **۱۵ دقیقه** برای اعلام پرداخت فرصت دارد. اگر مالک اصلاح رسید یا اطلاعات پرداخت را بخواهد، یک مهلت **جداگانهٔ ۱۵ دقیقه‌ای** برقرار می‌شود و قفل در همین مدت حفظ می‌شود. پس از اعلام پرداخت، تا تصمیم نهایی مالک سانس همچنان قفل است.
- رد اولیه می‌تواند بدون دلیل باشد؛ درخواست اصلاح یا رد نهایی نیازمند دلیل است. پایان مهلت درخواست را منقضی و قفل سانس را آزاد می‌کند. رویدادهای مهم برای مالک و بازیکن همان رزرو اعلان می‌شوند؛ لغو رزرو قطعی از سوی باشگاه نیز به بازیکن همان رزرو اطلاع داده می‌شود. Push خارج از برنامه نیازمند تنظیمات بالا است.
- رابط مدت را «۱.۵ ساعت» نشان می‌دهد. هر روز از نیمه‌شب به بازه‌های پیوستهٔ ۹۰ دقیقه‌ای تقسیم می‌شود؛ تعداد داخلی بازه‌ها در رابط به‌عنوان شمارندهٔ سانس‌ها نمایش داده نمی‌شود. رزروهای هم‌پوشان یک زمین با قفل تراکنشی رد می‌شوند.
- برنامهٔ عمومی فقط وضعیت کلی آزاد/رزروشدهٔ سانس را نشان می‌دهد؛ نام بازیکنان، مبلغ، رسید و گفت‌وگو برای دیگر بازیکنان قابل مشاهده نیست. جزئیات رزرو و مکالمه فقط برای مالک و بازیکن همان درخواست است.
- زمین از برنامهٔ جاری **بایگانی** می‌شود، نه اینکه سابقهٔ رزروهای آن پاک شود. برای جلوگیری از ناپدیدشدن رزرو باز، ابتدا درخواست‌ها و رزروهای آیندهٔ زمین باید تعیین‌تکلیف شوند. تاریخچه و گفت‌وگوهای زمین بایگانی‌شده از بخش آرشیو قابل مشاهده می‌مانند.
- رسید JPG، PNG، WebP یا PDF تا ۸ مگابایت در Storage نگهداری می‌شود و فقط مالک و بازیکن همان رزرو به آن دسترسی دارند. این اپ درگاه پرداخت ندارد؛ اعلام پرداخت و رسید در جریان فعلی دستی است.
- پرداخت تازه تا تأیید صاحب باشگاه در ماندهٔ حساب محاسبه نمی‌شود. پس از تأیید نهایی رزرو، یک سانس برنامه‌ریزی‌شده در دفتر حساب بازیکن ثبت می‌شود؛ مبلغ رزرو تا ثبت نتیجه به‌صورت موقت کنار گذاشته می‌شود و فقط حضور، غیبت یا لغو دیرهنگام هزینه ایجاد می‌کند. لغو به‌موقع پس از تأیید مالک بدون هزینه است و لغو از سوی باشگاه نیز هیچ هزینه‌ای ایجاد نمی‌کند. تشخیص به‌موقع/دیرهنگام دستی است، چون مهلت دقیق لغو تعریف نشده است.
- پرداخت بیرونیِ رزرو پس از تأیید مالک به‌عنوان اعتبار حساب ثبت می‌شود. هنگام پرداخت رزرو بعدی می‌توان اعتبار مثبت را تا سقف مبلغ رزرو مصرف کرد و فقط باقیمانده را دستی پرداخت کرد. هر سانس قیمت خودش را نگه می‌دارد تا تغییر نرخ بعدی روی سابقه اثر نگذارد.
- مبالغ به عدد صحیح تومان ذخیره می‌شوند. رکوردهای حساب و رزرو برای حفظ سابقه حذف فیزیکی نمی‌شوند.

## بررسی پیش‌نمایش

برای آزمایش واقعی Firebase، ورود، خواندن/نوشتن Firestore و آپلود Storage را از همان دامنه و شبکهٔ هدف امتحان کن. بازشدن Firebase Console به‌تنهایی دسترسی Auth یا Firestore از شبکهٔ کاربر را ثابت نمی‌کند. Push واقعی و انقضای سمت سرور نیز تا deploy و آزمون در پروژهٔ Firebase تأییدشده محسوب نمی‌شوند.
